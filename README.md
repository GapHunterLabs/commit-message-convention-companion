# Commit Message Convention Companion

IntelliJ-family plugin. Validates the commit message you are
**currently writing**, live, in the IntelliJ VCS Commit dialog —
against the [Conventional Commits](https://www.conventionalcommits.org/)
convention — and shows the exact rule it breaks before you commit,
instead of silently accepting or rejecting.

## Why it exists

An original idea, not a port of an existing competitor — validated
against `CONSTITUTION.md` §1's "Plan B permanente" discipline before
being built: (1) confirmed no plugin in this catalog does exactly this;
(2) confirmed buildable in the ~10-day budget with a platform mechanism
already stable (`CheckinHandlerFactory`/`CheckinHandler` — first use of
this specific mechanism in the Gap Hunter Labs catalog, its real
signature confirmed via `javap` against the platform jar rather than
guessed — see `SDK_GOTCHAS.md`). Same "apuesta consciente sin ancla de
mercado" treatment as Refactor Simulator / Test Scaffold Companion /
SQL String Concatenation Companion: v0.1 ships free, no time/marketing
investment disproportionate to real demand signal until there's
evidence of adoption.

## Differentiation vs. Committle — verified against real source code

The closest existing plugin in this exact space is **Committle**
(id 23100, 8,353 downloads, Free — `eugenekozhun/committle`). Its full
file tree was read directly from the public GitHub repo before this
plugin was built: Committle has its own Language/Lexer/Parser/
Highlighter (`CMTLexerAdapter`, `CMTParserDefinition`,
`CMTSyntaxHighlighter`), a `GenerateCommitMessageAction`, and variable
replacement services (`BranchTaskIdReplacer`, `BranchTypeReplacer`,
`FilePathScopeReplacer`) — **100% template generation/insertion**. It
has zero `Inspection`/`Annotator`/`Validator`-shaped file anywhere in
the repo that analyzes and flags errors in a message the user already
wrote by hand.

This plugin's angle is the opposite and complementary one: **validate
what the user already typed**, live, with the exact violated rule shown
— never generate or insert a template. Someone could reasonably use
Committle to generate a message and this plugin to validate it.

## What it checks (v0.1, Conventional Commits standard — all Free)

1. **Header shape**: first line matches `<type>(<scope>): <description>`
   or `<type>: <description>` — scope is optional.
2. **Type vocabulary, case-sensitive** per the real spec: `feat`,
   `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`,
   `chore`, `revert`. `Feat:`/`FEAT:`/`feature:` are all rejected as
   unknown types, exactly like the spec requires.
3. **Subject line length** — two thresholds, a deliberate choice
   documented here rather than picked arbitrarily:
   - **> 72 characters → hard warning** (blocks by default, requires
     "Commit Anyway"). 72 is the long-standing convention for keeping
     `git log --oneline` and GitHub's UI readable without wrapping.
   - **51–72 characters → soft suggestion only, never blocking.** 50 is
     the commonly cited "ideal" subject length, but treating anything
     past it as a hard block would be overly strict for a real team
     workflow — only the wrap-unfriendly 72 line is a real warning.
4. **No trailing period** on the description — common Conventional
   Commits/Angular convention.
5. **Merge commits are always skipped.** A message like `Merge branch
   'feature/x' into 'main'` or `Merge pull request #42 from ...` is
   generated by git itself, never typed by the user, and is detected
   and excluded before any rule runs.

## What v0.1 deliberately does NOT cover

Stated honestly, not silently half-handled:

- **Commit footers** (`BREAKING CHANGE: ...`, `Refs: #123`) — no
  parsing or validation of anything past the subject line's shape.
- **The `!` breaking-change marker** after type/scope (`feat!: drop
  support for Node 14`) — not recognized or validated as a special
  case in v0.1.
- **Configurable team rules** — a custom scope whitelist, a
  team-specific regex, a configurable length limit, shared via a VCS
  config file. This is a distinct, larger feature intentionally
  deferred to a possible future v0.2 Pro tier, not started, not
  promised (see `CONSTITUTION.md`'s monetization discipline: no
  disproportionate investment before real adoption signal).

## How it integrates with the IDE

Registered via `CheckinHandlerFactory` (extension point
`com.intellij.checkinHandlerFactory`), the platform's real, stable
mechanism for hooking into the VCS Commit dialog — distinct from a
`LocalInspectionTool` (which inspects source code, not the commit
message text box). `beforeCheckin()` runs synchronously right before
the commit executes; if the message has a real (Warning-level)
violation, a dialog shows every violation found and lets the user
choose "Commit Anyway" or "Cancel" — a soft-only suggestion (subject
line 51–72 chars) never blocks by itself.
